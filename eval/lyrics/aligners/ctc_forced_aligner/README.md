# ctc-forced-aligner backend — 2026-08-05 aligner shootout

Forced-alignment backend for the lyrics forced-aligner shootout
(`eval/lyrics/score_aligner.py`), using
[MahmoudAshraf97/ctc-forced-aligner](https://github.com/MahmoudAshraf97/ctc-forced-aligner)
(commit `11855d1de76af2b490dd2e8e2db2661805ae90a0`, 2026-07-12) with the
`MahmoudAshraf/mms-300m-1130-forced-aligner` wav2vec2-CTC model.

Unlike the audio-LLM backends elsewhere in this eval harness, this tool is
**not a transcriber**. It receives the FIXED reference text that
`qwen35-omni` already produced (`text-refs/<video_id>.json`, generated by
`push_text_refs.py`) plus the isolated-vocal WAV, and returns per-WORD
timestamps for that exact text via real CTC forced alignment — it never
re-transcribes or reinterprets the words.

## Files

- `run.py` — the canonical, self-contained per-fixture aligner. Same file
  pushed byte-for-byte to win-resolume and run there unmodified (the
  aligner itself needs the GPU/venv that only exists on win-resolume).
  CLI: `python run.py --wav <path> --text-json <path> --out <path>
  --star-frequency {none,segment}`.
- `push_text_refs.py` — generates the compact `{video_id, category, lines:
  [{text, text_sk}]}` reference files from the already-produced
  `qwen35-omni_<video_id>.json` raw reports. Writes locally only; the
  actual push to win-resolume is a handful of `FileWrite` calls (each
  compact file is a few KB).
- `batch_run.py` — Windows-side orchestrator. Imports `run.py`'s functions
  directly so the ~1.2GB model loads ONCE and is reused across all 44
  (22 fixtures × 2 configs) alignment calls instead of reloading per call.
  Isolates the poisoned fixture (`Xvm4_fWkXe8`) in its own subprocess with
  a 900s hard timeout, run LAST per config, so a hang/crash there can never
  block or kill the other 21 in-process runs.

## Traps hit and how they were resolved

1. **No PyPI wheels for `ctc-forced-aligner`, any platform.** Must build
   from source; needs a C++ compiler. See install step 3-4 above.

2. **`ctc_forced_aligner.alignment_utils.load_audio` shells out to a bare
   `"ffmpeg"` command with NO way to pass a full path via its API** — it
   relies entirely on `ffmpeg` being on `PATH`. This project's ffmpeg lives
   at `C:\ProgramData\SongPlayer\cache\tools\ffmpeg.exe`, not on PATH by
   default. `run.py::ensure_ffmpeg_on_path()` checks `shutil.which("ffmpeg")`
   and prepends the known directory to `os.environ["PATH"]` if missing —
   called at the top of every entry point (`run.py main()`,
   `batch_run.py main()`).

3. **This project's isolated-vocal WAVs are 32-bit float PCM (format tag
   3)**, not 16-bit integer PCM. Python's stdlib `wave` module cannot read
   them at all (`wave.Error: unknown format: 3`) — this broke the initial
   duration-fallback implementation on the very first real fixture. Fixed
   by never using `wave` for duration: `run.py::wav_duration_ms_fallback`
   reuses `ctc_forced_aligner`'s own `load_audio()` (ffmpeg-based, handles
   any PCM subtype) instead.

4. **Real digit characters in the reference text crash the aligner** —
   `AssertionError: m != 2` / `AssertionError: <star> != 2` inside
   `ctc_forced_aligner.alignment_utils.get_spans`. Root cause, traced via a
   direct re-run with full traceback capture: `p74PDWAFk0A`'s qwen35-omni
   reference text contains the literal token `"20"` (from "...you got 20
   more seconds..."). `get_alignments` builds its forced-alignment target
   sequence (`token_indices`) by silently DROPPING any character not in the
   model's vocabulary (`if c in dictionary`) — the MMS char-CTC vocabulary
   has no digit characters — but `get_spans` walks the UNFILTERED `tokens`
   list expecting a 1:1 character match against the (now shorter)
   `token_indices`-derived segments. The mismatch trips the assertion. This
   is a genuine upstream limitation for any reference text containing raw
   digits (not something we should route around by pre-editing the
   reference text — the task requires passing it through UNCHANGED). Caught
   per-fixture; the whole fixture falls back to all-untimed lines with the
   real exception recorded in `metadata.error`, and the rest of the batch is
   unaffected. Every OTHER of the 21 normal fixtures (no raw digits in their
   text) got 0% untimed lines.

5. **GPU VRAM contention with the sibling `LyricsAlignment-MTL` shootout run**
   — both run on the SAME single 8GB RTX 3070 Ti concurrently. Observed live:
   free VRAM swinging between ~200MB and ~7GB as the sibling loads/frees its
   own model between fixtures. The FIRST full batch run's model load hit a
   CUDA OOM and crashed the whole `batch_run.py` process before writing a
   single output file (model load happens once, outside any per-song error
   handling). Fixed with `run.py::load_model_with_retry` — up to 10 retries,
   30s fixed backoff, `torch.cuda.empty_cache()` between attempts — used by
   both `run.py`'s own CLI and `batch_run.py`. This is NOT a design flaw in
   the shootout itself; it's the correct behavior for two processes legitimately
   sharing one GPU.

6. **A hard OS-level subprocess crash (access violation, exit code
   `3221225477` = `0xC0000005`) on the poisoned fixture, in the FIRST full
   run**, killed the isolated subprocess before it could write ANY output —
   and the original `run_poisoned_subprocess` only wrote an all-untimed
   fallback file on `TimeoutExpired`, not on a non-zero exit code. Fixed:
   both failure branches (crash and timeout) now share one `write_fallback()`
   helper, so a crashed/killed poisoned-fixture subprocess can never leave a
   missing output file again. On the SECOND full run (after this fix), the
   poisoned fixture actually completed successfully in both configs (23.1s
   / 28.0s) — the crash appears to be a borderline, GPU-pressure-dependent
   failure mode rather than a deterministic one; both outcomes (clean
   success and hard C++-level crash) have now been directly observed on
   identical input.

7. **`mcp__win-resolume__FileWrite` silently truncates content over roughly
   1,500-1,700 characters when the payload is one pathological unbroken
   line with no newlines** (confirmed via a synthetic test) — but writes
   normal multi-line source files (up to ~20,000 chars, per this project's
   own `.claude/rules/lyrics-eval-backends.md`) correctly in one call.
   `mcp__win-resolume__FileRead` has a real, different ceiling: truncates
   at exactly 100,000 characters with an explicit `[... truncated at 100KB]`
   marker (not the ~20K figure the pre-existing rule doc states for
   *reads* — that number is a `FileWrite` limit only). All 44 real output
   files (max 74KB) were individually under that 100KB `FileRead` ceiling,
   but reading them all one-by-one through the agent's own context proved
   extremely wasteful in practice; the actual transfer of all 44 files used
   a temporary `python -m http.server` on win-resolume (`curl`'d down
   directly by the coordinating agent, bypassing the MCP text channel
   entirely) instead.

## Real CLI / API surface (verified from source, not the README prose)

`ctc_forced_aligner.align:cli()`'s actual argparse (`--star_frequency`
default `"edges"`, `--split_size` default `"word"`, `--batch_size` default
`4`, `--window_size` default `30`, `--context_size` default `2`,
`--compute_dtype` default `float16` on CUDA) is what `run.py` mirrors,
rather than inventing its own tuning. Full API trace, the `<star>` token
mechanics, and why forced alignment can NEVER leave an individual word
"not found" (only the whole call can fail) are documented in `run.py`'s own
module docstring — read it there; it is written to stay accurate as the
single source of truth for how this backend actually calls the library.

`--star-frequency {none,segment}` (this backend's flag) maps to the
library's own `star_frequency` `{"edges", "segment"}` — `none` (default)
is "the CLI's own default, i.e. without `--star_frequency segment`" per the
task brief; `segment` is the stronger setting. `backend_id` is
`ctc-forced-aligner` for `none` / `ctc-forced-aligner-star` for `segment`.

`LANGUAGE = "eng"` is used for all 22 fixtures, including `multi_language`
category ones — `ctc_forced_aligner.norm_config.py` (upstream) has NO
`eng`/`spa`-specific entries; every language outside
`{mon, khk, heb, tha, ara, arb, jav}` falls back to the identical shared
`"*"` config, and this backend never romanizes (English + Spanish are both
already Latin script, and the MMS model supports both natively) — so the
language argument has zero effect on this backend's behavior either way.
Confirmed by spot-checking `qwen35-omni`'s own reference text for 4
`multi_language` fixtures: plain English throughout regardless of the sung
language.

- Per-song alignment (excluding the poisoned fixture): mean 1.43s, min

- **Total wall-clock for the whole 44-output batch: ~130s (~2.2 minutes)**

  remarkably fast; the ~45-minute setup dominates total time by far.

## Known limitation this run surfaced (not fixed, reported honestly)

CTC forced alignment is, by construction, FORCED: `get_spans` walks the
merged-repeat CTC path expecting an exact character match for every target
word, so a successful call ALWAYS produces exactly one timestamp per input
word — there is no notion of "this word probably isn't really sung here."
On the poisoned fixture (`Xvm4_fWkXe8`, 395 reference lines, ~311 of them a
qwen35-omni degenerate repetition hallucination for a real ~4.6-minute
song), the aligner did NOT leave the excess hallucinated lines untimed —
it produced a monotonically increasing, plausible-looking timestamp for
ALL 395 lines, spread confidently but almost certainly WRONGLY across the
280.7s of real audio. This is architecturally different from what a
"graceful degradation" might look like for an ASR-style tool: a forced
aligner cannot express "I don't think this text is actually here" — it
will confidently mistime hallucinated text rather than admit the
uncertainty. See the scoring section below for the honest numbers this
produces on the poisoned fixture (0% within 400ms of gold, exactly as
expected for text that was never really sung).
